# Agentの役割を変えることと、見える情報を変えることは同じなのか

## 2026-09-28 更新：実モデルPilotに向けた準備

現在はbenchmark 2.0.0 / protocol 2.1。10 family・30 taskへ拡張し、
構造的なeasy / medium / hardを各10件用意した。正解候補が常に先頭だった
作問上の偏りも監査で見つけ、全条件に共通する再現可能な順序シャッフルで
対処した。変更前のfreeze・ソース・Mock結果は保存している。

現行のMock検証はPilot 12 run / 48 calls、全条件150 run / 510 calls。
実モデルは未実行であり、これらは研究仮説を支持する結果ではない。
有効な根拠・主張・insightの重複と独自貢献、collective coverage gainを
計測できる。1 workerを除いた指標は、回答を再生成せず根拠の喪失だけを
調べる近似なので、Agentの因果的な貢献そのものとは呼ばない。

実モデルPilotは事前固定した6 taskのC2/C3比較に限定し、48 callsを予定。
同じ6 taskで全5条件を回すと102 callsとなり、既定上限60を超えるためだ。
API認証情報と明示的なモデル選択・bindingが必要で、mainは無効化してある。
最新の手順は[実行準備](../READY_FOR_REAL_PILOT.md)、監査は
[benchmark audit](benchmark-audit.md)を参照。
以下は旧24 task版の検証と背景の記録として残す。新旧結果は混ぜない。

## 今回の結論から

比較のための実験基盤を実装し、Mock Providerで全経路を検証した。
ただし、**実際のLLMを使った比較実験はまだ行っていない**。
環境にAPI認証情報がなかったためである。

したがって「情報分離の方が優れている」「役割を変えても意味がない」とは
結論できない。ここで報告する数値は、情報境界・計測・分析が正しく動くかを
確認するための検証結果であり、LLMの能力を測った研究結果ではない。

## 何を調べたいのか

人間の集団では、同じ課題に向き合っていても、各人の経験、知識、判断基準は
異なる。その違いが、誰か一人では気づけなかった論点を生むことがある。

この話を、そのままAIの「会議アプリ」に置き換えたいわけではない。
問いはもっと基礎的だ。同じモデルに同じ情報を渡して役割だけを変えることと、
アクセスできる情報自体を変えることは、集団としての処理にどのような違いを
もたらすのだろうか。

ここでは前者をRole Diversity、後者を情報分離によるEpistemic Diversityと
呼ぶ。ただし、情報分離でモデルの学習済み知識や信条まで変わるわけではない。
操作しているのは、その実行で利用できる外部Evidenceの範囲である。

また、既存のMulti-Agentがすべて同一の知識しか持たないと決めつけない。
異なるモデルを使う研究や、情報非対称性を扱う研究も存在する。
今回の狙いは、役割と情報アクセスという二つの要因を分けて比較することだ。
確認した一次資料は[Related Work](related-work.md)にまとめた。

## 「3人」と「1人」を比べるだけでは足りない

情報分離した3 Agentが1 Agentより良くても、それが情報分離のおかげなのか、
単に呼び出し回数を増やしたおかげなのかは分からない。そのため5条件を置く。

| 条件 | Worker数 | 役割 | 見えるEvidence |
|---|---:|---|---|
| C0 | 1 | 中立 | 全部 |
| C1 | 3 | 全員同じ中立 | 全員が全部 |
| C2 | 3 | 分析・反証・相互作用の3観点 | 全員が全部 |
| C3 | 3 | 全員同じ中立 | 重複しない分割 |
| C4 | 3 | 3観点 | 重複しない分割 |

C1〜C4は同じモデル、生成設定、出力スキーマ、Tool権限、Worker数にする。
Toolは全条件で使用しない。役割設定は強い人格の演技ではなく、分析時に優先する
観点を短い文で与える。C4では特定の役割が有利な資料を担当し続けないよう、
taskとseedに応じて役割とpartitionの対応をランダム化する。

Workerの後ろには共通のSynthesizerを置く。ただし、Synthesizerが元の資料を
全部読み直せるなら、Workerの情報分離が何を生んだか分かりにくい。
そこで、受け取れるのはWorkerが公開した構造化Artifactだけにする。

## プロンプトではなく、Runtimeで分離する

「他の資料を見ないで」とプロンプトに書くのではない。
既存RuntimeのContextBuilderが、各Agentに許可された資料だけを取り出し、
切り離されたContextを構築する。AgentはGlobal Stateを受け取らない。

```text
全Evidence
  ├─ Policy A → Worker A → 公開Artifact A ─┐
  ├─ Policy B → Worker B → 公開Artifact B ─┼→ Synthesizer
  └─ Policy C → Worker C → 公開Artifact C ─┘
```

通信は自由会話ではなく、主張・洞察・根拠ID・不確実性を持つスキーマで行う。
実際にProviderへ渡ったContextと返却結果を保存し、別partitionのIDや監査用の
marker、gold annotationが混ざっていないかを検査する。

この研究コードは`experiments/epistemic-diversity/`に閉じ、`app/`を利用する。
Runtimeから研究コードへの逆向き依存はない。今回はRuntime本体を変更せずに
実験を構成できた。

## 24問の小さな制御ベンチマーク

二つのtask familyを用意した。一つは、障害調査などの分散Evidence統合。
もう一つは、システム構成や資源配分など、複数制約を合わせて判断する問題だ。

各taskには6個の関連資料と3個のdistractorがある。各Workerには関連資料2個と
distractor1個を割り当てる。中間的な洞察には3資料が必要なので、分離条件では
Worker一人では必要な根拠が揃わない。最終的には公開Artifactの統合が必要になる。

正解は評価用のgoldファイルへ分離する。Agentに渡すのは、候補となる判断規則、
報告語彙、資料だけである。正しい候補を示すgoldは見せない。

ただし24問は24個の独立した現実問題ではない。6テンプレートに4通りの状態を
与えた人工問題であり、同じグループ内の事実は一緒に変化する。関連性が既知の
資料を均等に分ける点も、現実より有利な条件だ。これは比較を制御するための
出発点であり、幅広い推論能力を測る完成済みbenchmarkではない。

## 何を「多様性」として測るか

言い回しや文章の長さが違うだけでは、有効な情報が増えたとは言えない。
そこで、根拠・主張・洞察の単位で測る。

主な指標は、最終正答、gold claimの回収率、Worker全体の関連Evidence回収率、
あるWorkerだけが提供した有効情報の割合、重複率、主張集合のJaccard類似度である。
矛盾、根拠のない主張、情報漏洩、token、呼び出し回数、latencyも記録する。

特に大事なのは、**分割すれば根拠の重複が減るのは、ある程度当然**という点だ。
固有寄与率が上がっただけで「賢くなった」とは言えない。最終的な正しさや
回収できた有効情報が増えたかを、別の指標で確認する必要がある。

同様に、共有条件では全資料へのアクセスが許可されている。
許可された情報が見えていることを「漏洩」と呼んで、情報分離が安全だと結論する
のは比較として不適切だ。そのため、権限違反の検出と、分離条件を基準にした
追加の資料露出を別々に記録している。

## 実際に実行したことと、その結果

まず2 task × 5条件＝10 runのMock pilotを実行した。境界、スキーマ、Runtimeに
問題がないことを確認してから、24 task × 5条件 × 2反復＝240 runを実行した。
呼び出しはpilot34回、全体816回。すべてMockであり、有料API呼び出しは0回である。

全条件で最終正答率と関連情報回収率は100%だった。共有条件の根拠重複率は約0.667、
分離条件は0。固有根拠の寄与率は共有0、分離1だった。境界違反、goldの混入、
矛盾、unsupported claimsの検出はすべて0だった。

これはRole Diversityが無意味という結果ではない。Mockは役割文を解釈せず、
与えられた資料と公開ルールだけを決定的に処理するからである。

一つ興味深い構造上の確認ができた。共有条件のWorkerは二つの必要な洞察を
生成できたが、分離条件のWorkerは一つも生成できなかった。それでも最後には、
Synthesizerが各Workerの事実を組み合わせ、二つとも回収した。

つまり分離により、局所的には推論材料が不足し、統合の責務が後段に移っている。
これは「単に同じContextへ違う役名を付けた実装」では生じない境界の違いだ。
ただし、実際のLLMがこの受け渡しをうまく行えるかは未確認である。

C2だけ成功/C3だけ失敗、またはその逆となる最終回答の組は見つからなかった。
存在しない失敗例を作って分析したことにはしていない。

## 統計を出しても、言えないことは残る

分析は同じtask同士のpaired comparisonを使う。反復はtask内で平均し、
平均・中央値・SD・IQR、差のbootstrap 95%区間、効果量、paired permutation testを
計算する。二値の成功にはexact McNemarを使い、事前指定した比較で多重性を補正する。

今回の主要指標は全taskで差が0だったため、区間も[0, 0]となった。
これは決定的なMockの動作を反映しただけであり、LLMの差がないことを高い確信度で
示すものではない。6テンプレート内の依存もある。研究上の効果とその確からしさは
まだ分からない、と明確に区切る必要がある。

## 次に何をするか

認証情報を用意した後、同じモデルでpilotを実行し、境界やスキーマの問題がなければ
事前に固定したmain subsetへ進む。標準予算はpilotとmainを合わせて最大180 calls、
予定は170 callsである。各送信前に永続ledgerへ予約し、失敗した呼び出しも数える。
価格が確認できない場合は金額を推測せず、costをnullとして残す。

その次に必要なのは、曖昧な資料、競合するEvidence、偏ったpartition、より多くの
独立したテンプレートを含む検証だ。ただし結果を見て都合のよい問題だけ選ばず、
新しいprotocolとして変更点を先に記録する。

役割だけの方が勝っても、情報分離が勝っても、差がなくてもよい。
目指しているのは特定の方式の優位性を証明することではなく、**Agentの何を
独立させると、協調の何が変わるのかを説明できるようにすること**である。
