# 内容検証と独立人手レビュー

## 対象と資料

source監査は元の30問×C3（90 Worker出力＋30 Synthesizer入力・最終回答）を全件対象にします。C1は同じroleで全文を見た参照、C2は旧主比較の参照です。C1/C2との照合資料は30問分用意しますが、人手判定の主対象はC3の30問です。新しい本比較終了後は24問×A/B/Cの72最終回答も検証します。

資料は二層に分けます。public-only資料には質問、原文、匿名化したWorker出力、実際の合成入力、回答を置きます。評価資料にはgold回答・支持文を置きます。入力作成プログラムへ評価資料を渡しません。集計結果を見せず、条件名をランダムなcase codeに置き換えます。閲覧順とmappingを記録します。文書量から条件を推測できる可能性があり、完全なblindとは主張しません。

## 一件ごとの判定

判定単位は「回答に必要な事実・関係」です。gold支持文だけを完全な事実一覧とみなさず、原文で支持された別表現・別支持経路も記録します。原文が足りず、モデルの事前知識で正答したと疑われる場合はその旨を記録し、確認できない内部推論を作りません。

| 項目 | 記録すること |
| --- | --- |
| 必要な事実 | 人物・日付・関係と、支持するsentence ID。新しく付与するfact ID |
| 局所での利用可能性 | どのWorkerがどの部分を見たか。一人で全経路を見られるか |
| 引用の適合性 | 引用文が、そのfindingsの主張を支持するか。yes/no/unclear |
| 抽出・公開の正しさ | 事実が正しく記載、欠落、誤記、判定不能のどれか |
| 受け渡し | 元payloadと合成入力artifactが内容同一か。機械照合結果も添付 |
| 合成の正しさ | 届いた事実を正しく統合、取り違え、不使用、判定不能のどれか |
| 最終内容 | 回答と根拠が原文で支持されるか。公式文字列スコアとは別に記録 |

原因ラベルは複数選択を許し、`local_information_gap`、`worker_omission`、`worker_error`、`transfer_mismatch`、`synthesis_error`、`undetermined`を使います。局所情報の不足だけで誤答の原因を確定しません。どの段階が原因か特定できなければ`undetermined`を残します。

個票には`study_id`、`case_code`、`question_id`、`reviewer_id`、`fact_id`、`source_sentence_ids`、公開出力と合成入力の該当箇所、上記判定、原因ラベル、短い根拠、確信度（high/medium/low）、判定時刻を持たせます。レビューIDから元の条件へのmappingは評価担当側に保存します。

## 独立性と合意形成

実験実装・モデル出力の作成者以外の2名が、同じ基準で別々に判定します。AIが作った自動レビューを、独立した人間のレビュー人数に数えません。

最初に旧Pilotの最初の2問で判定基準を校正し、合意した基準revisionを固定します。校正例も本監査に含めますが、一致率は残り28問で計算し、校正例を使ったことを明記します。新しい比較の72回答は全件独立判定します。

独立判定を保存してから協議します。判定項目と各原因ラベルごとに、単純一致率、判定数、yes/no/unclearの分布を報告します。協議後の結果を独立判定に上書きせず、別versionに保存します。解消しない不一致はunclear/undeterminedのまま残します。

担当者を確保できない場合は、public-only資料と空の個票形式を用意してpendingと記録します。作成者のレビューは進められますが、独立人手検証と区別して報告します。レビューを受けるために外部へデータを送る操作は、別途その共有先・公開範囲を決めてから行います。

## 生成への影響を防ぐ

監査ラベルやレビュー結果は、質問の選定、引用原文の選択、共通Prompt、中立文の調整に使いません。新しい入力は`PLAN.md`の機械的規則で固定します。新比較の回答のgold scoringとレビューは本比較の生成終了後に行います。
