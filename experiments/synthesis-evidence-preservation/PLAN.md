# WorkerからSynthesizerへの情報保持：探索的介入研究

計画日：2026-09-30。研究ID：`synthesis-evidence-preservation-v1`。
本書は次の研究の計画仕様です。実装・freeze・実生成の完了は意味しません。

## 1. 研究の区切りと仮説

前研究の完了監査は150ケース・510正常生成・511予約を確認しています。全30問のAnswer F1はC2が0.758、C3が0.599でした。前研究の主比較は当時未観測だった24問のC3−C2で−0.15643でした。

次の研究は、性能差の機構を調べる段階です。

- H1：保存済みWorker出力に引用元原文を添えると、要約のみよりAnswer F1が高くなる。
- H2：その差は、同程度の入力量を足した中立文対照と比較しても観測される。
- 診断的な問い：原文→Worker公開出力→Synthesizer入力→最終回答のどこで必要な事実が欠落・変形・不使用になるか。

引用原文の追加は、要約の曖昧さを減らすことや注意を引くことでも効き得ます。H1/H2の結果だけで圧縮による情報欠落を唯一の原因と断定しません。引用されなかった文は介入で戻らないため、改善しなくても情報欠落一般を否定できません。

今回使う24問の結果は既に観測しています。前研究の「fresh24」という名称を、新しい研究に対する未観測標本の意味では使いません。今回は既存24問での探索的検証です。

## 2. 研究手順と対象

1. 追加生成なしで、既存30問のC3を全件監査する。C1を同じneutral roleの参照条件、C2を従来比較の参照として使う。
2. `REVIEW.md`の基準でレビュー資料を作り、独立レビューを依頼できる状態にする。担当者未確保でも、機械的なsource確認と入力作成は進める。
3. 3問×A/B/Cで動作確認する。9回の新規Synthesizer生成。
4. 技術gate合格後、既存24問×A/B/Cを一反復で実行する。72回の新規Synthesizer生成。
5. 全条件の結果・失敗・資源使用量を集計し、レビュー結果と合わせて解釈する。

動作確認の3問は`study.json`に固定した監督の出自、ブログ執筆者の生年、司会者の生年月日の問題です。本比較の24問は元の30問manifestの7〜30番目で、同JSONにIDを列挙しています。成績・監査ラベルによる質問の追加・除外・置換はしません。

動作確認と本比較では2問が重なります。動作確認9件を本比較72件に流用せず、独立した質問数にも加えません。3問の改善率で次の実行可否を決めません。

## 3. 固定するものと3条件の介入

| 要素 | 全条件共通の仕様 |
| --- | --- |
| 元Worker | 同じ質問の保存済みC3のworker_0〜worker_2。新規Worker生成0回 |
| 順序 | 元のworker_0, worker_1, worker_2の順序とpayloadを保持 |
| 共通入力 | 元のSynthesizer request.contextを基にする。条件間で共通部分を同一にする |
| 変更箇所 | 共通のinstructionと`context.inputs.supplementary_material`のみ |
| 元の記録 | 改変せず、新しい実行ID・条件・元参照は新campaignの外側の記録に持つ |
| 最終出力 | 元の`hotpot.final.v1`（answer、evidence_ids、uncertainty） |
| 引用権限 | 元3 Workerの公開payloadが引用したIDの集合。全条件で同一 |
| 評価 | 元と同じ公式scorer・正解、モデルから分離した評価処理で使用 |

元のJSONファイルhashと、payloadのcanonical JSON hash（UTF-8、key sort、空白なし、Unicode保持）を両方記録します。元ファイルのbyte保持と、replay時のpayload内容の同一性を区別します。元Worker応答とSynthesizerに渡ったartifactが一致しない場合は、生成前に停止して異常を報告します。

Aの補足は空文字です。Bは引用原文、Cは固定中立文を補足欄へ入れます。B/Cには同じ補足欄名を使い、condition名やgold情報をモデル入力へ入れません。

入力Schemaは新研究専用の`evidence-preservation.input.v1`を追加し、`supplementary_material: str`だけを必須項目として許可します。未知fieldを拒否し、Aも空文字を明示します。旧研究の`hotpot.input.v1`は変更しません。最終出力Schemaと公式予測export形式は既存のものを使います。

共通instructionは`study.json`の文字列をそのまま使います。元の「raw documentsを見ない」という指示は、原文追加と矛盾するため残しません。3条件全て同じ新instructionで生成し、旧最終回答をAとして代用しません。新Aと歴史的C3の差は再実行差として別記します。

### B：引用元原文の選択

Worker順に、各payloadの`findings[*].evidence_ids`、続いて`uncertainty.evidence_ids`を読み、IDの初出順で重複を除きます。引用IDを、その質問のpublic sentencesと照合します。各IDが引用したWorkerの元入力に存在したことも確認します。

各文は`[ID] title (sentence_index)\ntext`の形式で全文を並べ、文間に空行を置きます。title、sentence_index、textはpublic記録の値です。正解、gold支持文、人手の原因分類で原文を選びません。未知ID、質問違い、private fieldの混入は停止条件です。空の引用集合ならA/B/Cの補足は全て空とし、介入なしの件数を報告します。

### C：入力量対照

`assets/length-control.txt`を順に繰り返し、末尾を単語境界で短くして、Bに近いtoken量の文字列を作ります。末尾の候補は短い順に列挙し、Bとの差が最小のものを選び、同差なら短い方にします。task-specificな人物名・日付・Evidence IDや別質問の文は使いません。生成AIに対照文を作らせません。

tokenizerの語彙とchat templateが対象Ollamaモデルに対応することを、モデルmetadata・ローカル資産のhashとtemplateで確認します。共通system suffixを含め、実際に送るmessagesの全文を計測します。生成tokenやJSON全bodyのbyte数はinput tokensとして扱いません。

補足token差はmax(1 token, B補足の5%)以内、全promptのtoken差はmax(1 token, B全promptの5%)以内とします。満たせない場合は入力作成段階で停止します。実応答のprompt_eval_countも保存し、B/Cで後者の許容差を超えた場合は以後の生成を停止し、token量を揃えた比較の完了を宣言しません。

中立文にも注意分散の影響はあり得ます。B−Cは「この中立文対照との差」であり、完全な総compute統制を意味しません。A/B/Cのoutput tokensと処理時間も異なり得るため、資源使用量を併記します。

## 4. 実行設定、予算、開始条件

モデルは元と同じdigestのQwen3:14b、Ollama 0.34.4、native `/api/chat`を使います。temperature0、think=false、context8192、input上限4096、output上限4096、deadline1200秒、concurrency1です。tool、repair、retry、同campaignのresumeは使いません。CodexのChatGPT認証をそのまま使い、研究runnerがCodex認証を変更しません。

input上限は実装時に送信前にtoken計測し、応答側のprompt_eval_countも検査します。長すぎる入力は切断・除外せず生成前に停止します。上限や設定の変更が必要なら、出力を見る前に計画revisionと新freezeへ明記し、旧revisionでは実行しません。

予定81回は動作確認9＋本比較72の合計です。動作確認上限9、全体hard ceiling81、失敗予約も消費します。追加の診断生成やtoken計測用生成を81回の外側で行いません。必要なら別計画にします。1回1200秒のdeadline単純合計は最大27時間ですが、これは実測所要時間の予測ではありません。

質問は`study.json`の順で実行します。質問内の条件順は、`SHA256("20260930:phase:question_id:arm")`の昇順で固定します。phaseは`smoke`または`main`、armはA/B/Cです。

全81入力・条件順・source参照・hash・scorer・tokenizer・共通指示・中立文・Schema・設定・分析定義・コードを実生成前にfreezeします。source/model/host確認、offline tests、81件Mockの合格を開始条件にします。人手レビュー担当者の未確保は生成の技術gateにせず、独立レビュー完了の判定に使います。

動作確認後は正常終了・Schema・引用権限・入力同一性・token差・保存・台帳のgateだけを評価します。全生成が終了するまでgold scoringは行わず、改善率でPromptや補足を調整しません。異常時は停止し、残り予定と消費済み予約を報告します。

## 5. 分析と解釈

分析対象は本比較24問の全72件です。技術失敗時は完了した問だけの平均を完成結果として提示せず、incompleteと件数を報告します。技術成功の誤答や空答えは公式scorerでそのまま評価します。

- 主評価：質問ごとの公式Answer F1差B−Aの平均。
- 計画した対照比較：同じくB−C。C−Aは中立文の干渉を見る記述的比較。
- その他：各条件のEM、Support F1、Joint F1、支持文recall、改善/同点/悪化の問数、input/output tokens、call latency、Aと旧C3の再実行差。
- 不確実性：質問単位のpaired bootstrapを10,000回、seed20260930で実施しpercentile 95%区間を示す。探索的な条件付き区間で、確認的な有意性の宣言やendpointの事後変更はしない。
- 感度確認：public文書titleを共有する質問をつないだ連結成分でcluster bootstrapする。成分数と規模を報告し、1成分のみならcluster区間は計算不能として記述値を示す。title共有が全ての意味的依存を捉えるとは主張しない。
- 監査ラベル別の差は探索的な補助結果。小群の比率だけで機構を確定しない。

解釈は平均差の符号と各問の変化から記述します。B−AとB−Cがともに正なら、引用原文の追加がこの条件で改善したという所見です。B−Aのみ正なら、中立文対照を含む解釈に留めます。どちらも改善しない場合も全結果を残し、仮説を支持しなかったと報告します。

この研究で直接答えるのは、固定したWorker出力へのSynthesizer入力介入の効果です。情報分割そのものの純粋な効果、全C3低下の原因割合、他モデル・全devへの一般化は含めません。
